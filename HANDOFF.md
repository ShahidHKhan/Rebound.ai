## Read this first: how this project is being built

The user is building this app **as a hands-on AI-engineering learning exercise**, not just shipping a product. The established collaboration pattern for feature work:

- Break work into small, numbered tasks. For each: explain *what* and *why*, then give full code as fenced blocks for the user to paste into their own editor and run themselves.
- Wait for their result (they paste terminal output back) before moving to the next task.
- The user sometimes says "implement steps X" or "do it yourself" — that's an **explicit, one-time override** for that specific step, not a standing change. Default back to guide-mode afterward unless told otherwise.
- Verification commands (`pnpm typecheck`, `pnpm test`, running a script to confirm something works) are fine to run directly regardless of mode — the restriction is specifically about writing the *feature implementation* for them.
- The monorepo scaffold (Turborepo, Prisma schema, tRPC skeleton, `packages/clinical-rules`) was built directly by Claude *before* this pattern was established — everything since (Flow A, Flow B, the API layer) followed it.

**Do not skip this** — reverting to "just implement everything directly" defeats the actual point of the exercise for the user.

## What Rebound.ai is

AI-powered PT app (see PRD for full detail). Core loop: onboarding → AI drafts a two-session daily exercise regime (Flow A) → user logs pain/completion daily → a recursive agent adjusts the regime weekly (Flow B) → a separate real-time escalation monitor watches every log for pain spikes. Heavy emphasis on rules-based safety guardrails wrapping the LLM, not just LLM judgment alone — see PRD's "Clinical Risk Framing" section.

- **Privileged connection (`DATABASE_URL`, unchanged)** — owns the tables, so Postgres RLS never applies to it by default. Used unchanged by `packages/agents` and `/api/cron/*`, which have no single "current user" to scope to (Flow B iterates many users per run). Zero code changes needed in either.

- **Verified two ways, not one**: (a) raw-script proof via `prismaRls` directly, with application-level ownership checks completely out of the picture — confirmed a user can't read another user's rows even via an explicit `WHERE userId = <other user>` clause (RLS overrides the query, not just supplements it), and that the admin flag genuinely grants cross-user access; (b) full regression through real `createCaller` calls — onboarding submit → poll → regime getById/activate → sessionLog.create → workoutSession.today → admin.metrics, all against a fresh test user, including the slow Haiku classifier call now happening inside the RLS transaction. **Three former "Known gaps" closed out — user-requested, end of session.**

- **`AdjustmentEvent.wasReversed` now has a real writer.** `markReversedEvents` (`packages/agents/src/escalation-actions.ts`) fires whenever `applyEscalationRollback` runs. Deliberately scoped to escalation rollbacks only — the one structurally-unambiguous "walk-back" signal in this data model, since Flow B's own scheduled adjustments always create a *new*, higher-numbered regime version regardless of whether the LLM's decision was "progress" or "rollback" (that distinction only lives in free-text `rationale`, not a structured column), so it can't be reliably detected as "undoing" a prior event without fuzzy heuristics. An event E (created at regime version vE→) counts as reversed once a later rollback lands the active regime back at vE's *starting* version or earlier — for either trigger type, matching the PRD's "tracked across both scheduled_adjustment and escalation_rollback trigger types" framing. **Verified with a real boundary-condition test**: v1→v2→v3 chain, partial rollback v3→v2 (not all the way to v1) — correctly left the v1→v2 event `wasReversed: false` (v2 is still where things landed) while marking v2→v3 `true` (that one got undone). Caught and fixed a real bug in the process: the rollback event was initially marking *itself* as reversed (its own `fromRegime` outranked the target version) — fixed by excluding the new event's own id from the candidate query. Re-verified against the existing `escalation-e2e-test` regression script, not just the synthetic scenario.
- **Cross-checked the risk-tier/change-ceiling numbers against the literature the PRD cites by name** (research only — did not touch the numbers themselves, that's real PT-sign-off territory). Findings, worth relaying to whoever eventually does that sign-off: the "10% rule" is weaker evidence than the PRD's "evidence-informed" framing implies — never validated in a peer-reviewed trial, originated as 1980s coaching-book tradition; a key systematic review found *no difference* in injury risk between 10% and 24% average weekly load increases, with the actual injury-risk signal being large single-session spikes (30%+, or exceeding 110% of the longest recent session) rather than a strict weekly percentage. Separately, the 0–3/4–6/7–10 pain traffic-light split doesn't precisely match the specific Silbernagel et al. pain-monitoring model the PRD gestures at (that one uses a single ≤5/10 threshold during loading, not a three-bucket system) — the tri-color split IS a legitimate, ubiquitous general clinical pain-scale convention, just not literally that specific study's model.

**Notification system — built, local-only architecture, delivery not yet confirmed on real hardware.** Implements the PRD's two-fixed-notifications-per-day mechanic (morning wake, evening user-picked time).
- **Architecture decision, made explicitly with the user, not assumed**: local (on-device) notifications via `expo-notifications`, not server-driven push. Server push would have needed a new push-token field, a real IANA timezone field (never existed — only the naive `wakeTimeMinutes` int), a new Vercel cron running every 5–15 min, and a new job to pre-create future `WorkoutSession` rows (they're only ever created for "today", once, at `regime.activate` — still true, see gaps below). Local notifications sidestep all of that by construction.
- `apps/mobile/lib/notifications.ts` (new) — single exported `syncDailyNotifications(sessions)`, called from a `useEffect` + `AppState` listener in `HomeScreen` (`app/(app)/index.tsx`) on every mount and app-foreground. Cancels and reschedules two fixed-identifier local notifications (`daily-session-morning`/`daily-session-evening`) using `workoutSession.today`'s real `scheduledAt`/`completedAt` values directly — no server round-trip or client-side re-computation needed. If a slot's time for today has already passed (or is already completed), approximates tomorrow's occurrence by shifting the time-of-day +1 day; self-corrects to the real value next time the app opens. Permission requested automatically on first regime-having `HomeScreen` mount (no settings toggle, matching the PRD's "fixed, not configurable" framing); fails silently, never throws, if denied.
- Required exactly one native rebuild (`expo-notifications` ships native code) — done. Everything after that was pure JS and hot-reloaded through the existing dev-client + Metro connection.
- **Still has a temporary dev-only debug log** in `HomeScreen`'s effect (`console.log("[notifications] currently scheduled:", ...)`, gated `if (__DEV__)`) — left in on purpose to help confirm real-device scheduling; remove once that's verified.
- **Verified so far**: typecheck clean across the monorepo, the native module links correctly (app boots without a crash on the real device), the permission dialog appears. **NOT yet verified**: actual OS-level delivery while the app is backgrounded/killed, lock-screen banner/sound behavior, or the multi-day drift-and-self-correct behavior for the evening slot — confirming this was the entire reason for migrating off Appetize, but the session moved into fixing UI bugs (found via the real device) before circling back to actually check delivery. **This is the single most important thing to verify first in the next session.**

## Tooling gotchas hit this session (avoid rediscovering these)

1. **Every new `packages/*/tsconfig.json` needs `"include": ["src", "scripts"]` and must NOT set `rootDir`.** Setting `rootDir: "src"` while `scripts/` is also included causes "File is not under rootDir" errors. Hit this identically for `packages/db` and `packages/agents`.
2. **VS Code can silently use the wrong TypeScript version** in this monorepo — `apps/mobile`'s Expo scaffold pins a different major TS version than everything else. Root `.vscode/settings.json` now pins `typescript.tsdk` to the repo root's own install. If "cannot find name console/fetch/process" type errors reappear despite correct tsconfig, check the TS version in the status bar first, not the code.
3. **Anthropic tool-use calls need `max_tokens: 4096`, not 2048**, in both `flow-a.ts` and `flow-b.ts` — echoing back a full 10-12 exercise regime plus reasoning routinely needs more than the smaller default.
4. **`after()` (Next.js) throws when called outside a real HTTP request.** This matters when testing tRPC procedures via `createCaller` from a plain script — there's no live request scope. `onboarding.submit` wraps `after()` in try/catch with a fire-and-forget fallback specifically for this; it's intentional, not a bug to "fix."
5. **`RegimeGenerationJob.userId` is a required FK to `User`.** The user row must exist before the job row is created — this is why `upsertUserForOnboarding` runs synchronously in `onboarding.submit` before job creation, not inside the backgrounded `draftAndPersistRegime`.
6. **Test scripts using a fixed `test-user-*` id must reset prior state before re-running**, respecting FK delete order: `AdjustmentEvent` and `SessionLog` before `Regime` (neither cascades; only `RegimeExercise` cascades from `Regime`). Every script that creates data follows this pattern now — copy it rather than re-deriving.
7. **Never put real secrets in any `.env.example` file** — those are tracked by git (the real `.env` files are gitignored). This happened twice this session and had to be cleaned up both times. Real credentials belong only in `apps/web/.env`, `packages/db/.env`, `packages/agents/.env`, `packages/api/.env` (all gitignored, all currently pointing at the same real Supabase DB / Anthropic key — check those files directly rather than asking the user to repaste credentials).
8. **On Windows, `prisma generate` fails with `EPERM: operation not permitted, rename ... query_engine-windows.dll.node`** if the Next.js dev server (or anything else with the Prisma client loaded) is currently running — it locks the native engine DLL. Ask the user to stop `pnpm --filter @rebound/web dev` before running `prisma generate` or `prisma db push` (push itself succeeds; it's the auto-triggered generate step after it that fails), then they can restart it once generation succeeds.
9. **To force a fast, deterministic LLM failure for testing** (e.g. exercising a retry-exhaustion path) without waiting on real slow failures or burning real API calls: override `process.env.ANTHROPIC_API_KEY` to a garbage value and load `@rebound/agents` via a *dynamic* `import()` afterward, from a script with no static import of it. `client.ts` builds the Anthropic client eagerly at module load, so a static import (hoisted before any code runs) would still capture the real key. Used to verify the preset-fallback path this session.
10. **Supabase's connection pooler routes by a `<role>.<project-ref>` username**, not the bare Postgres role name — that's why the default role is `postgres.<ref>`, not `postgres`. A new role's connection string needs that same suffix or you get `FATAL: no tenant identifier provided (external_id or sni_hostname required)`. Hit this creating the `rebound_app` role for RLS.
11. **A Prisma `Prisma.TransactionClient` (the `tx` inside `$transaction(async (tx) => ...)`) deliberately doesn't expose `$transaction` itself** — TypeScript will fail to compile any code that tries to nest one. If a function's `ctx.prisma` might sometimes be a transaction client (true for everything downstream of `protectedProcedure` now — see RLS above), don't call `.$transaction()` on it; the operations are already atomic within the outer transaction, so just run them directly.
12. **To verify an Expo app actually builds without a simulator/device**: `expo start --web` (needs `react-native-web`/`react-dom` installed), then `curl` the root page to get the HTML shell, `grep -o 'src="[^"]*"'` out the bundle URL it references, and `curl` *that* directly — this forces Metro to actually compile the whole route tree. Watch the bundler's own log for a `Web Bundled ... (N modules)` line with no preceding error; don't trust grepping the bundle's JS text for strings like "Cannot find module" — Metro's own error-formatting runtime code contains those exact strings, so they're present in every bundle whether or not anything actually failed.
13. **Prisma's `update`/`create` data objects treat an explicit `undefined` field as "don't touch this," not "set to null."** Used deliberately in `upsertUserForOnboarding` — passing `submission.wakeTimeMinutes` straight through means a re-submission that skips it (e.g. declined location permission) leaves any previously-saved value alone rather than wiping it. Don't "fix" this into `?? null` without realizing it changes that behavior.
14. **`suncalc`'s `getTimes(...).sunset` is typed `Date | null`, and that's not over-defensive typing** — sunset genuinely doesn't occur on some days near the poles (24h daylight/darkness). `regime.activate` falls back to the 6pm placeholder for this case the same as "no location supplied," rather than crashing or ignoring the type.
15. **When retroactively marking rows from inside the same code path that just created the triggering row** (see `markReversedEvents` in `escalation-actions.ts`), explicitly exclude the new row's own id from the candidate query. Easy to miss — a naive "find all unmarked rows that qualify" query will happily match the row you just inserted if its own before/after state satisfies the same condition. Caught this one via a real test, not by inspection; write the boundary-condition test before trusting logic like this.
16. **A Windows Firewall permission dialog silently hangs any *non-interactive* attempt to start Metro in LAN mode** (`expo start --dev-client`, no `--tunnel`) — the dialog is a GUI popup, so a background/scripted shell with no display session just stalls forever with zero console output change, indistinguishable at a glance from a genuinely slow bundler startup. `--tunnel` mode doesn't trigger this (routes through Expo's relay instead of binding a LAN-listening port), which is why it worked fine non-interactively earlier in the same session. Always start LAN-mode Metro from the user's own interactive terminal, not a background tool call.
17. **`TaskStop` (or Ctrl+C) on a background shell task does not reliably kill the underlying detached Node child process on Windows.** Hit this twice: once made a wrong "it's stuck" diagnosis because the wrapper was killed but the real Metro process kept running and eventually finished on its own; once had to explicitly `Get-NetTCPConnection`/`Stop-Process -Force` the actual PID before Prisma's Windows DLL lock (gotcha #8) would release. Always verify with `Get-NetTCPConnection -LocalPort <port>` / `Get-Process` before trusting that something was actually stopped, especially before re-running a command that binds the same port.
18. **`expo start --tunnel` auto-installs `@expo/ngrok` globally via `npm install -g`, but a pnpm-managed project can't resolve npm's global install location** — the CLI reports success installing it, then immediately fails to find it. Fix: `pnpm add -D @expo/ngrok` as a real local devDependency instead of relying on the automatic global install.
19. **`pnpm-workspace.yaml`'s `allowBuilds`/`minimumReleaseAgeExclude` maps can silently block every pnpm command** (not just the one that triggered them) if left with a placeholder value instead of a real boolean — hit this with a literal `dtrace-provider: set this to true or false` left over from a previous install. If pnpm suddenly starts failing everything with `[ERR_PNPM_IGNORED_BUILDS]`, check this file first, not the command you're actually trying to run.
20. **EAS Build's default (non-dev-client) profile bakes the JS bundle into the binary at build time** — every JS/UI change needs a full ~15-minute cloud rebuild to see reflected. Setting `developmentClient: true` + `distribution: "internal"` on the `eas.json` profile switches to a build that connects to a live Metro server instead, matching normal Expo Go-style DX — only *native* dependency changes need a rebuild after that. Worth setting up before doing any real iteration, not after.
21. **Appetize.io's cloud-hosted Simulator can't reach a private LAN backend** (`localhost` or a `192.168.x.x` address means nothing from Appetize's own cloud). Raw `ngrok http <port>` needs a free account + authtoken even for ad-hoc use (`ERR_NGROK_4018` without one) — Cloudflare's quick tunnel (`cloudflared tunnel --url http://localhost:<port>`, no account needed at all) is the faster unblock for this specific "I just need a temporary public URL" case. Moot once testing moves to a real device on the same WiFi as the dev machine, which was the actual long-term fix here.
22. **iOS requires enabling "Developer Mode"** (Settings → Privacy & Security → Developer Mode, then a device restart) for any non-App-Store install — ad-hoc, dev-client, or TestFlight alike. This is separate from trusting the developer certificate (Settings → General → VPN & Device Management) — you need both, and Developer Mode is easy to miss since the error message ("Developer Mode Required") only appears the first time you actually try to open such an app, not at install time.
23. **Apple Developer Program enrollment ($99/yr, Individual) removes the Mac requirement for real-device testing entirely, not just the App Store distribution requirement.** EAS Build always compiles in the cloud regardless of host OS; ad-hoc distribution (`eas device:create` + a device-targeted build profile) and TestFlight are both web/CLI-driven. The Mac was only ever needed for *local* Xcode-based signing (the free-personal-team path) — paying for the Developer Program sidesteps that path entirely rather than just unlocking a paid version of it.
24. **`eas device:create` and first-time `eas build` credential setup are inherently interactive** (menu selection, and an Apple ID login the first time EAS needs to talk to App Store Connect) — cannot be run non-interactively or from a shell with no stdin attached. Hand these specific commands to the user to run in their own terminal rather than attempting `--non-interactive` workarounds.
25. **Prisma's `db push` data-loss confirmation prompt also cannot be answered non-interactively.** Use `--accept-data-loss` explicitly once you have real confirmation from the user that the loss is intentional (it's irreversible against a live database) — combine with `--skip-generate` to dodge gotcha #8's Windows DLL lock, then run `prisma generate` as a fully separate step once nothing else holds the engine DLL.
